# LoomX Assistant 长响应导致界面“假死”感知

## 状态

- 类型：待调查的独立稳定性问题
- 优先级：高
- 发现方式：Browser Bridge 端到端验证期间人工观察
- 影响范围：LoomX Assistant 长时间流式输出、推理或多步骤工具循环
- 本记录不纳入 `fix-browser-bridge-connectivity` 的实现范围，避免把两个独立问题混合修复。

## 现象

使用 `Deepseek / deepseek-v4-pro` 执行较长的多步骤任务时，模型输出过度冗长，LoomX Assistant 长时间保持“运行中”状态，用户感知为界面假死。期间缺少足够明确的进度、持续活动与可立即生效的中止反馈，容易被误判为整个应用卡死。

## 风险

1. 用户无法区分“模型仍在生成”“工具循环未结束”“请求已失去进展”和“UI 真正卡死”。
2. 过多增量更新可能放大 Markdown 重排、消息集合通知、自动滚动与 Session 持久化成本。
3. 取消操作若不能快速打断上游读取、AgentLoop 和 UI 投影，会进一步强化假死感知。
4. 长推理/工具循环缺少输出预算与步骤预算时，单轮运行可能持续占用大量时间和上下文。

## 后续调查要求

1. 分别测量模型网络读取、AgentLoop、Session 持久化、Markdown 渲染和 UI Dispatcher 投影耗时，确认阻塞发生在哪一层。
2. 记录安全的运行指标：首 token 延迟、最近一次增量时间、累计字符数、事件数、步骤数、取消到停止耗时；禁止记录正文和工具参数。
3. 对比“高频小 delta”和“低频批量 delta”，验证 UI 更新节流/合并是否能消除卡顿。
4. 验证取消是否能在明确时限内中止 HTTP 流、工具执行与后续 UI 投影。
5. 检查超长 reasoning/content 的显示上限、折叠策略、单轮 token/字符预算和 AgentLoop 最大步骤策略。

## 预期改进方向

- 为流式 UI 投影增加批量合并或节流，避免每个小 delta 都触发完整渲染与布局。
- 显示可判断活性的状态：最近响应时间、当前步骤、已运行时长，并区分“仍有流量”和“长时间无进展”。
- 提供始终可用且有即时反馈的取消操作；取消后禁止迟到事件继续写入当前视图。
- 为单轮输出、reasoning 和工具循环设置可配置预算，达到阈值后要求模型收敛或安全终止。
- 对超长过程内容默认折叠/虚拟化，避免消息树和 Markdown 控件无限增长。

## 验收草案

- 在持续两分钟的模拟流式响应中，窗口保持可交互，输入、滚动和取消操作有可见响应。
- 高频增量输入不会导致 UI Dispatcher 队列无界增长。
- 点击取消后，在约定时限内停止网络读取和 UI 增量投影，并恢复可发送状态。
- 用户能够从状态区明确判断当前仍在生成、正在执行工具、等待重试或已经停滞。
- 日志只包含安全指标，不包含 prompt、响应正文、Secret 或工具参数。
