# 透明窗口运行时刷新设计

## 目标

修复桌面端透明窗口设置在运行中不生效的问题：用户切换“透明窗口”或调整“透明程度/磨砂程度”后，当前窗口应立即更新；窗口启动时也应根据已保存设置建立正确的系统透明材质。系统不支持所选材质时，界面仍需使用可见且稳定的回退背景。

## 根因与约束

- Avalonia 的系统透明材质选择属于窗口级状态，不能假设窗口显示后重新设置 `TransparencyLevelHint` 就会重新创建合成层。
- 页面各层使用共享的 `SolidColorBrush` 资源。运行时修改 Alpha 必须以固定的颜色基线计算，不能基于上一次修改后的画刷继续缩放。
- 透明开关关闭时必须明确使用不透明背景；开启时窗口本身保持透明，让系统材质或回退画刷负责窗口底层呈现。
- 不修改数据库字段、设置范围、页面绑定和自动保存协议。

## 方案

### 窗口初始化

`MainWindow` 在构造/初始化阶段配置默认的透明级别提示和回退画刷。应用启动读取设置后，调用统一的外观应用方法设置画刷 Alpha 与开关状态。窗口级材质提示只在窗口尚未显示时确定，避免依赖显示后的动态重建。

### 运行时刷新

保留 `ApplyAppearance` 作为唯一入口，但将职责拆成两部分：

1. 根据固定的基线颜色和传入参数计算所有玻璃画刷的 Alpha，并更新共享资源；
2. 根据透明开关切换窗口背景。透明开启时使用 `Transparent`，关闭时使用不透明基线副本。

运行时不再把改变材质算法当作必须重建窗口的操作。算法选择在当前平台可用时沿用已有材质级别顺序；不支持时由 Avalonia 使用回退画刷。

### 数据流

设置控件双向绑定到 `SettingsViewModel`。属性变化继续触发实时预览和延迟自动保存：

`Slider/Toggle/ComboBox -> SettingsViewModel -> ApplyAppearance -> 共享画刷/窗口背景`

应用启动路径继续先读取配置，再初始化窗口并应用同一入口，确保启动状态与实时预览使用完全相同的计算逻辑。

## 错误与兼容性

- 透明度和磨砂值继续在窗口入口处钳制到 `0-100` 与 `0-64`，避免异常配置破坏渲染。
- 找不到资源时保持现有透明回退，不抛出 UI 初始化异常。
- 不支持 Acrylic/Mica 的平台继续使用 `TransparencyBackgroundFallback` 与不透明模式回退，不影响页面交互。

## 测试

- 单元测试验证透明度计算始终基于固定基线，连续应用不同值不会累积误差。
- 单元测试验证透明开关分别产生透明窗口背景和不透明窗口背景，并更新透明级别提示。
- 保留现有设置页契约测试，确保滑块范围和双向绑定不回退。
- 构建桌面端并运行完整测试集，确认 Avalonia XAML 与运行时外观入口均可加载。
