# Assistant 消息队列（Codex 交互体验）后续需求

## 1. 背景

AskUser 会使当前 AgentLoop 等待结构化用户决策。用户不希望等待期间输入框被锁死，而希望像 Codex 一样继续组织后续消息。当前 change 先实现顺序入队、删除和自动出队的最小占位；本文件记录完整产品方向，供后续独立 Comet/OpenSpec change 推进。

## 2. 产品目标

- 用户在 AI 工作、工具运行或 AskUser 等待期间始终可以继续撰写后续消息。
- 用户能清楚区分“已发送到当前轮次”“等待发送”“正在调度”的消息。
- 队列默认保持严格串行，不让多个 AgentLoop 并发写同一会话。
- 用户可以在消息尚未正式发送前编辑、排序、删除或改变调度方式。
- 队列与会话绑定，不因页面导航或切换会话而误发。

## 3. 目标交互

### 3.1 队列列表

- 队列显示在输入框上方，按发送顺序编号。
- 每项显示文本预览、创建时间与当前状态。
- 支持展开查看完整内容。
- 支持删除尚未发送的项目。
- 支持把队列项恢复到输入框进行编辑。
- 支持拖动或键盘方式调整顺序。

### 3.2 调度动作

后续版本评估并实现三类动作：

1. **加入队列**：当前轮次完整结束后按 FIFO 发送。
2. **Steer 当前任务**：在安全边界把新指令提供给当前 AgentLoop，而不是开启并发轮次。
3. **停止并发送**：取消当前轮次，等待取消收敛后立即发送指定消息。

三类动作必须在 UI 上使用不同文案和状态，不允许同一个发送按钮静默改变语义。

### 3.3 失败恢复

- Provider/网络失败时暂停自动出队，保留队首和剩余项。
- 用户可以重试队首、跳过队首、重新编辑或删除。
- 不得因为一个失败项自动连续发送后续消息。
- 应明确区分模型已接收但响应失败与消息尚未发送，避免重复请求。

### 3.4 会话与持久化

- 队列项必须保存 SessionId 和稳定 Id。
- 切换会话后只显示目标会话队列。
- 后续评估将未发送队列持久化到应用数据库，使异常退出后可以恢复。
- 恢复后默认保持暂停，必须让用户确认是否继续自动发送，避免过时消息静默执行。

### 3.5 AskUser 协作

- AskUser 卡片回答属于当前轮次，不触发队列提前出队。
- 当前轮次可能连续产生多个 AskUser；队列始终等待该轮次最终完成。
- 用户可以在 AskUser 显示期间添加、编辑、排序或删除队列项。
- 若用户选择停止当前任务，活动 AskUser 必须先幂等取消，然后才能调度“停止并发送”的消息。

## 4. 当前简版占位

`fix-assistant-decision-subscription-lifecycle` 只交付：

- 运行中发送入队；
- 顺序显示；
- 删除未发送项；
- 当前轮次正常结束后 FIFO 出队；
- 失败/停止后暂停；
- SessionId 隔离；
- 内存生命周期。

简版数据模型需要保留稳定 Id、SessionId、创建时间和显式状态，后续不得通过替换整个模型来增加编辑、排序或 Steer。

## 5. 后续启动条件

开始完整实现前，通过 Comet 创建 `enhance-assistant-message-queue` OpenSpec change，并重新确认：

- Steer 可接入的 AgentLoop 安全边界；
- 队列持久化表结构与数据库迁移；
- 已发送/未发送的精确确认点；
- 会话切换和应用重启恢复策略；
- 队列编辑、排序、无障碍键盘操作和移动端/窄窗口布局。
